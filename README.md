# Практикум по подготовке к реализации ActionFlow

Этот каталог содержит последовательную программу из одиннадцати небольших работ,
близких к первому модулю ActionFlow — контролю клиентских переписок. Каждая
работа создаётся с нуля в отдельном каталоге и проверяет один понятный механизм.

Полное условие находится в файле
[responseflow-practice.md](responseflow-practice.md). Готовые синтетические данные лежат в каталоге [synthetic-data/responseflow/](synthetic-data/responseflow/README.md).  Не нужно придумывать переписки, ожидаемые ситуации или правила приоритета: они уже подготовлены и являются частью условий.

Для разработчиков с небольшим опытом подготовлены
[отдельные подробные инструкции по каждой работе](tasks/README.md). В них есть
команды установки, каркасы модулей, импорты, описание классов и функций, примеры
вызова, начальные тесты и ожидаемые промежуточные результаты. Общие правила
начала работы и сдачи собраны в [памятке студента](student-guide.md).

## Что будет создано

1. Импортёр сообщений с защитой от повторов.
2. Сборщик упорядоченного окна переписки.
3. Поиск обращений без ответа.
4. Контроль обещаний и просрочек.
5. Поиск претензий и запросов документов.
6. Подключение LLM через прокси VseLLM.
7. Хранилище ситуаций и сообщений-оснований.
8. Расчёт приоритета и рекомендации следующего действия.
9. Очередь менеджера с переходами между состояниями.
10. Повторный прогон размеченных данных и отчёт о качестве.
11. Сквозное приложение ResponseFlow.

Работы 01–10 автономны: результат предыдущей работы копировать не требуется.
Работа 11 собирает изученные части в одну небольшую программу. Такой порядок
позволяет разбирать ошибки по одному механизму, а не сразу во всём приложении.

## Ограничения

- Python 3.12 или новее;
- `uv` для создания окружения и закрепления версий библиотек;
- Pydantic, Typer, pytest, клиент OpenAI в работе 06 и FastAPI в работе 09;
- локальные файлы JSONL и SQLite;
- никаких Docker, PostgreSQL, Redis, очередей сообщений и облачных служб;
- никаких настоящих данных клиентов;
- проверки по умолчанию не обращаются к сети;
- автоматические проверки не требуют языковой модели: работы 05 и 06 используют
  готовые заглушки; настоящий вызов VseLLM запускается отдельно и вручную.



## Общие команды проверки

В каждом решении README должен содержать команды, которые наставник может
скопировать без исправлений:

```bash
uv run ruff check .
uv run pytest -q
uv run python -m compileall -q src tests
```

Для работ с командной программой добавляется один полный ручной сценарий на
данных из `data/fixtures/`.

## Общие правила приёмки

Работа принимается, если:

- все обязательные проверки проходят на чистом каталоге;
- неизвестные поля и неверные значения входных данных отклоняются;
- дата и время всегда содержат часовой пояс;
- идентификатор рабочей области передаётся явно и данные областей не смешиваются;
- повторная обработка тех же исходных данных не создаёт дубликаты;
- каждая обнаруженная ситуация содержит ссылки на точные сообщения-основания;
- предметные правила не зависят от командной строки, FastAPI или SQLite;
- ошибка одной строки сообщает имя файла и номер строки;
- секреты и сетевой доступ для демонстрации не нужны;
- README объясняет устройство решения и приводит ожидаемый результат запуска.

Красивый экран не заменяет корректную обработку данных, доказуемые основания и
автоматические проверки.
