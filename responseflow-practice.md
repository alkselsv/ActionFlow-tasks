# Пошаговый практикум ResponseFlow

## Результат подготовки

Необходимо последовательно создать одиннадцать небольших реализаций, повторяющих главную цепочку ActionFlow:

```text
сообщение → контекст → обнаруженная ситуация → приоритет → действие → контроль
```

Задания намеренно не требуют сложной инфраструктуры. Входные данные поступают из файлов, состояние хранится в памяти, JSONL или SQLite, внешние службы заменяются программными заглушками. Главная цель — научиться точно моделировать данные, сохранять основания вывода, безопасно повторять обработку и измерять качество.

## Как организовать решения

Подробные учебные инструкции вынесены в каталог [`tasks/`](tasks/README.md): по
одному файлу на каждую работу. Там находятся каркасы модулей, примеры функций и
тестов, пояснения библиотек и порядок реализации. Общие правила подготовки,
проверки и сдачи находятся в [памятке студента](student-guide.md).

Каждая работа выполняется в отдельном каталоге:

```text
intern-tasks/
  01-message-import/
  02-conversation-window/
  03-unanswered-detector/
  04-commitment-control/
  05-semantic-situations/
  06-llm-situation-analyzer/
  07-finding-store/
  08-priority-and-action/
  09-manager-inbox/
  10-quality-replay/
  11-responseflow-local/
```

Минимальная раскладка каждой работы:

```text
01-message-import/
  pyproject.toml
  README.md
  src/message_import/
  tests/
  data/fixtures/
```

Начальная настройка:

```bash
uv init --package --name message-import --python 3.12
uv add 'pydantic>=2.8,<3' 'typer>=0.12,<1'
uv add --dev 'pytest>=8,<9' 'ruff>=0.6,<1'
mkdir -p tests data/fixtures
```

Для другого задания замените имя пакета. Файл `uv.lock` сохраняется вместе с
решением.

Рекомендуемые общие настройки:

```toml
[tool.pytest.ini_options]
pythonpath = ["src"]

[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
```



## Как пользоваться готовыми данными

Перед каждой работой прочитайте
`synthetic-data/responseflow/README.md`. Копируйте указанные в условии файлы в
`data/fixtures/`, не меняя содержимое и имена. Временная точка анализа во всех
проверках фиксирована: `2026-09-15T15:00:00+03:00`. Нельзя использовать текущее
время компьютера, иначе результаты станут неповторяемыми.

В данных есть две рабочие области — `north` и `south`. Большинство сценариев
относятся к `north`; область `south` нужна для проверки изоляции. Все компании,
люди, переписки и проекты вымышлены.

## Единые предметные понятия

- **Сообщение** — неизменяемое наблюдение конкретной редакции сообщения из чата.
- **Окно переписки** — упорядоченный отрезок сообщений, переданный анализатору.
- **Ситуация-кандидат** — результат анализатора до сохранения и устранения повторов.
- **Ситуация** — сохранённая карточка, требующая решения сотрудника.
- **Основание** — точная ссылка на сообщение, подтверждающее вывод.
- **Ключ повтора** — вычисляемая приложением строка, связывающая повторные
обнаружения одной проблемы.
- **Решение менеджера** — подтверждение, отклонение, откладывание или закрытие.

## Работа 01. Надёжный импорт сообщений



### Зачем это нужно

История чата может загружаться несколько раз, а сообщение может быть
отредактировано. Программа должна отличать повтор той же редакции от новой
редакции и не терять исходный внешний идентификатор.

### Что создать

Пакет `message_import` с файлами:

```text
models.py
reader.py
repository.py
service.py
cli.py
```

Скопируйте `messages/messages.jsonl`, `messages/revisions.jsonl` и файлы из
`invalid/`.

### Обязательные модели

```python
class MessageRevision(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    workspace_id: str
    conversation_id: str
    external_id: str
    revision: int
    sender_id: str
    sender_role: Literal["customer", "employee", "system"]
    sent_at: datetime
    observed_at: datetime
    text: str
    reply_to_external_id: str | None = None
    source: Literal["telegram", "max", "import"]

class ImportReport(BaseModel):
    read: int
    created: int
    unchanged: int
    rejected: int
```

Запись однозначно определяется четвёркой `workspace_id`, `conversation_id`,
`external_id`, `revision`. Если эта четвёрка повторяется с тем же содержимым,
получается `unchanged`. Если содержимое отличается, импорт завершается понятной
ошибкой о конфликте; существующая запись не перезаписывается.

### Пошаговая реализация

1. Создайте строгую неизменяемую модель сообщения.
2. Проверьте наличие часового пояса у обеих дат и непустой текст после удаления
  пробелов по краям.
3. Реализуйте чтение JSONL построчно, не загружая весь файл в память.
4. Добавьте номер строки и путь к файлу в сообщение об ошибке.
5. Создайте хранилище в памяти и службу импорта.
6. Добавьте файловое хранилище JSONL с безопасным повторным запуском.
7. Отсортируйте выдачу по `sent_at`, затем по `external_id`, затем по `revision`.
8. Добавьте команду `import-file` и команду `history`.
9. Импортируйте основную историю дважды и покажите, что второй запуск ничего не
  добавил.
10. Импортируйте `revisions.jsonl`: у сообщения `n-001-006` должны стать доступны
  две редакции, причём исходная остаётся в истории.



### Как выглядит готовое решение

```text
$ ... import-file data/fixtures/messages.jsonl
прочитано=43 создано=43 без_изменений=0 отклонено=0
$ ... import-file data/fixtures/messages.jsonl
прочитано=43 создано=0 без_изменений=43 отклонено=0
$ ... history --workspace north --conversation conv-n-001 --message n-001-006
редакции: 1, 2
```



### Обязательные проверки

- повторный импорт не увеличивает число записей;
- новая редакция не заменяет старую;
- одинаковый внешний идентификатор в разных беседах не конфликтует;
- наивная дата без часового пояса отклоняется;
- повреждённая строка сообщает номер `2`;
- конфликтующая редакция не изменяет хранилище;
- данные `north` нельзя получить запросом для `south`.



### Готово, если

Все проверки проходят, ручной сценарий даёт указанные счётчики, а служба импорта
ничего не знает о Typer и способе хранения.

## Работа 02. Сборка окна переписки



### Зачем это нужно

Анализатору нельзя отдавать случайный набор сообщений. Нужен воспроизводимый,
ограниченный отрезок истории с участниками, проектом и точным временем анализа.

### Что создать

Пакет `conversation_window`:

```text
models.py
catalog.py
window_builder.py
serializer.py
cli.py
```

Используйте `messages/messages.jsonl`, `messages/revisions.jsonl`,
`catalog/participants.json` и `catalog/projects.json`.

### Обязательный результат

```python
class ConversationWindow(BaseModel):
    workspace_id: str
    conversation_id: str
    project_id: str
    analysis_time: datetime
    messages: tuple[MessageView, ...]
    omitted_before: int
```

`MessageView` содержит внешний идентификатор, роль, отображаемое имя, время,
текст и ссылку на сообщение, на которое дан ответ. Секретные поля каталога в
окно не попадают.

### Правила

- берётся только последняя редакция каждого сообщения, известная на момент
анализа;
- сообщения позже `analysis_time` не включаются;
- основной предел — 12 последних сообщений;
- если первое взятое сообщение является ответом на более раннее, добавляется
исходное сообщение, даже если получится 13 сообщений;
- системные сообщения сохраняются, но не считаются ответом сотрудника;
- чужая рабочая область всегда отклоняется.



### Пошаговая реализация

1. Загрузите каталоги участников и проектов в строгие модели.
2. Свяжите беседу с одним проектом и проверьте совпадение рабочей области.
3. Выберите последнюю редакцию по наибольшему номеру.
4. Отбросьте сообщения из будущего.
5. Отсортируйте оставшиеся сообщения устойчиво.
6. Возьмите последние 12 записей и посчитайте `omitted_before`.
7. При необходимости добавьте сообщение, на которое ссылается первая запись.
8. Подставьте отображаемые имена участников.
9. Сериализуйте окно в один объект JSON с одинаковым порядком полей.
10. Добавьте команду `build`.



### Точный пример

Для `conv-n-001` при времени анализа `2026-09-15T15:00:00+03:00` текст сообщения
`n-001-006` должен быть из редакции 2: «Исправленную смету пришлю сегодня до
18:00». Сообщение `n-001-013` из будущего в окно не попадает.

### Обязательные проверки

- сообщения упорядочены от старых к новым;
- выбрана последняя известная редакция;
- будущее сообщение исключено;
- ссылка на раннее сообщение расширяет окно;
- неизвестный участник даёт ошибку с его идентификатором;
- смешение `north` и `south` невозможно;
- повторная сборка даёт полностью одинаковый JSON.

## Работа 03. Обнаружение обращения без ответа



### Зачем это нужно

Первый полезный механизм ResponseFlow — найти содержательный вопрос клиента,
который остался без реакции сотрудника дольше допустимого срока.

### Что создать

Пакет `unanswered_detector`:

```text
models.py
business_time.py
question_rules.py
detector.py
cli.py
```

Используйте сообщения, проекты и `policies/response-policy.json`.

### Упрощённые правила этой работы

Сообщение считается обращением, если роль равна `customer` и выполняется хотя бы
одно условие:

- текст содержит знак вопроса;
- начинается со слов «подскажите», «уточните», «пришлите», «когда», «можно»;
- содержит фразу «ждём ответ».

Обращение считается отвеченным, если после него и до времени анализа есть
непустое сообщение сотрудника. Системное сообщение и другое сообщение клиента
ответом не являются. Для первого варианта достаточно календарных минут; затем
добавьте рабочее время по правилам файла настроек.

### Результат анализатора

```python
class FindingCandidate(BaseModel):
    type: Literal["unanswered"]
    subject_key: str
    summary: str
    evidence_message_ids: tuple[str, ...]
    waiting_minutes: int
    due_at: datetime
```

`subject_key` имеет вид
`unanswered:<conversation_id>:<external_id>`. Текст краткого описания не должен
зависеть от случайности или языковой модели.

### Пошаговая реализация

1. Напишите проверки распознавания обращения отдельно от расчёта времени.
2. Найдите все обращения клиента в окне.
3. Для каждого обращения найдите первое последующее сообщение сотрудника.
4. Исключите отвеченные обращения.
5. Рассчитайте срок ответа по категории проекта.
6. Не создавайте ситуацию до истечения срока.
7. Соберите основание только из исходного обращения.
8. Упорядочите результаты по сроку, затем по идентификатору сообщения.
9. Добавьте рабочие часы: понедельник–пятница, 09:00–18:00 по Москве.
10. Сделайте команду `detect`, принимающую фиксированное время анализа.



### Эталон при полном наборе данных

Должна быть обнаружена ситуация для `n-001-012` в беседе `conv-n-001`.
Сообщение `n-002-003` не считается оставленным без ответа: после него есть ответ
`n-002-004`. Сообщение `n-006-002` ещё находится внутри допустимого срока.

### Обязательные проверки

- знак вопроса и ключевая фраза распознаются;
- благодарность без вопроса не распознаётся;
- сообщение сотрудника закрывает только предыдущие обращения;
- системная запись не считается ответом;
- граница срока проверяется до секунды;
- вечер пятницы и утро понедельника считаются по рабочему времени;
- результат содержит точный идентификатор основания;
- порядок входных строк не меняет результат.

## Работа 04. Контроль обещаний и просрочек



### Зачем это нужно

Сотрудник может пообещать клиенту результат к определённому времени. Даже если
клиент больше не пишет, невыполненное обещание должно стать контролируемой
ситуацией.

### Что создать

Пакет `commitment_control`:

```text
models.py
deadline_parser.py
completion_rules.py
detector.py
cli.py
```

Используйте `messages/messages.jsonl`, `messages/revisions.jsonl` и
`policies/date-phrases.json`.

### Поддерживаемые формулировки

Нужно обработать только заранее оговорённые формы:

- «сегодня до ЧЧ:ММ»;
- «завтра до ЧЧ:ММ»;
- «до ДД.ММ.ГГГГ ЧЧ:ММ»;
- «в течение N часов».

Обещанием считается сообщение сотрудника, содержащее одно из слов «пришлю»,
«отправлю», «подготовлю», «исправлю», «сообщу» и поддерживаемую дату. Разбор
естественного языка общего назначения не требуется.

Обещание считается выполненным, если после него сотрудник написал сообщение со
словами «отправил», «направил», «готово», «исправлено» и это сообщение появилось
не позже времени анализа. Если срок ещё не наступил, создаётся `commitment`, а
если наступил — `delay`.

Если клиент после обещания отвечает именно на него и пишет «не получили»,
«всё ещё нет» или «когда сможете», такое сообщение становится дополнительным
основанием той же ситуации. Оно не создаёт второе обещание и не меняет ключ
предмета.

### Обязательные поля результата

- тип `commitment` или `delay`;
- срок;
- идентификатор сообщения с обещанием;
- идентификатор подтверждения выполнения либо `None`;
- короткое описание;
- ответственная роль `account_manager`;
- ключ предмета `commitment:<conversation_id>:<message_id>`.



### Пошаговая реализация

1. Отделите извлечение срока от обнаружения обещания.
2. Всегда используйте часовой пояс исходного сообщения.
3. Для «сегодня» и «завтра» берите календарную дату сообщения.
4. Отклоняйте невозможные даты и отрицательное число часов.
5. Найдите обещания сотрудников.
6. Найдите возможное подтверждение после каждого обещания.
7. Сравните срок с фиксированным временем анализа.
8. Для открытого обещания сохраните исходное сообщение и подходящие повторные
   обращения клиента. Для выполненного обещания открытую ситуацию не создавайте.
9. Обработайте новую редакцию сообщения без создания второго обещания.
10. Добавьте команду вывода результатов в JSONL.



### Эталонные результаты

- `n-001-006`, редакция 2: просрочка, срок `2026-09-14T18:00:00+03:00`;
  основания: `n-001-006`, `n-001-010`, `n-001-012`;
- `n-003-002`: открытое обещание, срок `2026-09-15T17:30:00+03:00`;
- `n-004-002`: выполнено сообщением `n-004-003`, поэтому открытая ситуация не
создаётся.



### Обязательные проверки

- каждая поддерживаемая форма даты разбирается;
- неподдерживаемая фраза не угадывается;
- редакция 2 заменяет редакцию 1 при анализе;
- срок ровно в момент анализа уже считается наступившим;
- подтверждение до обещания не подходит;
- выполненное обещание не создаёт открытую ситуацию;
- неверная дата даёт предметную ошибку, а не необработанное исключение.

## Работа 05. Претензии и запросы документов



### Зачем это нужно

Одних формальных правил недостаточно для всех формулировок. В этой работе студент
осваивает заменяемый смысловой анализатор, но все проверки выполняются без сети
по готовой заглушке.

### Что создать

Пакет `semantic_situations`:

```text
models.py
analyzer.py
fake_analyzer.py
normalizer.py
service.py
cli.py
```

Используйте `analyzer/fake-results.json`, сообщения и
`expected/semantic-findings.jsonl`.

### Собственный договор анализатора

```python
class SemanticAnalyzer(Protocol):
    def analyze(self, window: ConversationWindow) -> tuple[SemanticResult, ...]: ...

class SemanticResult(BaseModel):
    model_config = ConfigDict(extra="forbid")
    type: Literal["complaint", "document_request", "manager_attention"]
    confidence: float = Field(ge=0, le=1)
    summary: str
    recommended_action: str
    evidence_message_ids: tuple[str, ...]
    subject_key: str
```

Заглушка выбирает результат по сочетанию рабочей области и беседы. Поле
`window_checksum` в готовом файле служит меткой версии набора и включается в
журнал вызова, но вычислять его в этой работе не требуется. Если беседа
неизвестна, заглушка возвращает пустой список. Служба обязана проверять, что
каждое основание действительно присутствует в переданном окне.

### Правила нормализации

- краткое описание: от 10 до 240 символов;
- рекомендация: от 10 до 300 символов;
- повторяющиеся идентификаторы оснований удаляются с сохранением порядка;
- результат с уверенностью ниже `0.60` отбрасывается;
- тип и `subject_key` не исправляются догадкой;
- отсутствие основания делает весь отдельный результат недействительным, но не
мешает сохранить другие корректные результаты окна.



### Пошаговая реализация

1. Создайте строгие входные и выходные модели.
2. Опишите собственный интерфейс анализатора.
3. Реализуйте заглушку из готового файла.
4. Проверьте диапазон уверенности и длины строк.
5. Проверьте принадлежность оснований окну.
6. Нормализуйте повторяющиеся основания.
7. Отфильтруйте низкую уверенность.
8. Соберите отчёт: принято, отброшено по порогу, отклонено как ошибочное.
9. Обработайте несколько результатов одной беседы независимо.
10. Добавьте команду `analyze-all`.



### Эталон

В полном наборе принимаются: претензия `n-002-003`, запрос УПД `n-005-001` и
ситуация для внимания менеджера `n-007-003`. Низкоуверенная запись для

### Обязательные проверки

- заглушка полностью воспроизводима;
- неизвестное окно не вызывает сетевой вызов;
- низкая уверенность отбрасывается на точной границе;
- чужое основание отклоняется;
- ошибка одного результата не теряет остальные;
- два одинаковых основания превращаются в одно;
- `south` не может ссылаться на сообщение из `north`.

Модель должна вызвать функцию `report_customer_situations`. Схема аргументов

рекомендацию, идентификаторы сообщений-оснований и ключ предмета.

После вызова обычный код обязан:

- разобрать JSON;
- запретить неизвестные поля и типы;
- проверить диапазон уверенности;
- убедиться, что все основания присутствуют в переданном окне;
- удалить повторы оснований;
- применить порог уверенности;
- сохранить имя модели, версию запроса и расход токенов.

### Ограничения безопасности

- использовать только синтетические данные;
- не печатать ключ и полный запрос в журнал;
- не хранить ключ в `.env.example`;
- не отправлять сообщения из другой рабочей области;
- ограничивать размер окна до вызова;
- выполнять не более одного настоящего вызова в ручной проверке;
- не давать LLM изменять состояние карточки и выполнять внешние действия.

1. Создать модели структурированного ответа.

### Обязательные проверки

### Готово, если

## Работа 07. Карточка ситуации, основания и устранение повторов



### Зачем это нужно

Периодический анализ снова и снова видит одну проблему. Он должен обновлять одну
карточку, а не засорять очередь копиями. Основания при этом хранятся отдельно и
не теряются.

### Что создать

Пакет `finding_store`:

```text
models.py
key_builder.py
repository.py
service.py
history.py
```

Используйте `expected/all-candidates.jsonl` и
`expected/candidate-updates.jsonl`. Хранилище — SQLite из стандартного модуля
Python.

### Модели

```python
class Finding(BaseModel):
    finding_id: UUID
    workspace_id: str
    conversation_id: str
    type: str
    subject_key: str
    deduplication_key: str
    status: Literal[
        "open", "acknowledged", "snoozed", "resolved", "reopened", "rejected"
    ]
    first_detected_at: datetime
    last_detected_at: datetime
    occurrence_count: int

class Evidence(BaseModel):
    finding_id: UUID
    message_external_id: str
    added_at: datetime
```

Ключ повтора вычисляет код: нормализованные `workspace_id`, `conversation_id`,
`type`, `subject_key` соединяются и пропускаются через SHA-256. Анализатор не
имеет права передавать готовый ключ.

### Поведение

- первый кандидат создаёт карточку со счётчиком 1;
- повтор обновляет `last_detected_at`, описание, рекомендацию, уверенность и
увеличивает счётчик;
- уже известное основание повторно не добавляется;
- новое основание добавляется к той же карточке;
- закрытая карточка переоткрывается только при новом основании;
- повтор старых данных не переоткрывает карточку;
- все изменения записываются в историю событий.



### Пошаговая реализация

1. Создайте модели и допустимые состояния.
2. Напишите чистую функцию построения ключа.
3. Создайте таблицы `findings`, `evidence`, `finding_events`.
4. Добавьте уникальные ограничения для ключа повтора и пары
  «карточка — основание».
5. Реализуйте создание в одной транзакции.
6. Реализуйте повторное обнаружение.
7. Реализуйте безопасное закрытие.
8. Реализуйте правило переоткрытия.
9. Верните историю в хронологическом порядке.
10. Проверьте повтор всей пачки кандидатов.



### Точный ожидаемый сценарий

После двух обработок `all-candidates.jsonl` число карточек не меняется, а их
`occurrence_count` равен 2. После закрытия ситуации по `n-001-006` повтор старого
кандидата оставляет её закрытой. Запись из `candidate-updates.jsonl` добавляет
основание `n-001-014` и переводит её в `reopened`.

### Обязательные проверки

- ключ стабилен и не зависит от регистра случайных пробелов;
- два типа для одного сообщения дают разные карточки;
- повтор пачки не создаёт строк-дубликатов;
- ошибка при добавлении основания откатывает всю операцию;
- закрытая карточка без новых оснований остаётся закрытой;
- новая улика безопасно переоткрывает карточку;
- рабочие области изолированы на уровне запросов и ограничений.

## Работа 08. Приоритет и следующее действие



### Зачем это нужно

Менеджеру мало знать, что проблема существует. Нужно единообразно объяснить,
почему она важна и что сделать дальше. Эти решения должны быть прозрачными и
проверяемыми.

Пакет `priority_and_action`:

```text

cli.py
```

Используйте `expected/all-candidates.jsonl`, `catalog/projects.json` и
`policies/priority-policy.json`. Для отдельной проверки надбавки за повторное
обнаружение используйте строку из `expected/candidate-updates.jsonl`: признак
`repeated_detection` уже подготовлен в её поле `flags`.

### Результат

```python

    finding_key: str
    priority: Literal["low", "medium", "high", "critical"]
    score: int = Field(ge=0, le=100)
    reasons: tuple[str, ...]
    recommended_action: str
    responsible_role: str
    action_due_at: datetime
```



### Правила расчёта

Начальная оценка берётся из таблицы по типу ситуации. Затем прибавляются баллы:
ключевой клиент, просрочка более суток, явная угроза остановки работ, повторное
обнаружение. Итог ограничивается диапазоном 0–100. Границы уровней берутся из
файла настроек. Каждая прибавка обязана создать человекочитаемую причину.

Рекомендуемое действие выбирается таблицей по типу. Для критического уровня к
нему добавляется требование немедленно уведомить руководителя. Срок действия
рассчитывается от времени анализа, а не от времени запуска программы.

### Пошаговая реализация

1. Проверьте файл настроек: границы возрастают, типы не повторяются.
2. Рассчитайте начальные баллы.
3. Примените надбавки независимыми чистыми функциями.
4. Ограничьте результат диапазоном.
5. Преобразуйте число в уровень.
6. Соберите причины в постоянном порядке.
7. Выберите роль ответственного.
8. Выберите рекомендацию.
9. Рассчитайте срок действия по уровню.
10. Выведите очередь: сначала критические, затем по сроку и ключу.



### Эталонные ориентиры

Просроченная смета для ключевого клиента «Северный ветер» должна иметь более
высокий уровень, чем обычный запрос УПД. Ситуация `manager_attention` для проекта
`aurora` должна стать критической из-за угрозы остановки работ. Каждая строка
отчёта содержит не только уровень, но и список сработавших правил.

### Обязательные проверки

- граничные значения уровней относятся к правильному уровню;
- итог никогда не выходит за 0–100;
- порядок причин воспроизводим;
- неизвестный тип не получает выдуманную рекомендацию;
- неверный файл настроек отклоняется до обработки;
- фиксированное время анализа даёт фиксированный срок;
- изменение порядка кандидатов не меняет результаты.

## Работа 09. Очередь менеджера



### Зачем это нужно

Обнаруженная ситуация полезна только тогда, когда человек может увидеть основания, принять решение и оставить объяснение. В этой работе создаётся небольшой программный интерфейс без отдельного внешнего интерфейса.

### Что создать

Пакет `manager_inbox`:

```text

repository.py
service.py
dependencies.py
routes.py
main.py
```

Установите `fastapi`, `uvicorn` и `httpx`. Используйте `inbox/seed.json`.

### Маршруты

```text
GET  /workspaces/{workspace_id}/findings
GET  /workspaces/{workspace_id}/findings/{finding_id}
POST /workspaces/{workspace_id}/findings/{finding_id}/acknowledge
POST /workspaces/{workspace_id}/findings/{finding_id}/snooze
POST /workspaces/{workspace_id}/findings/{finding_id}/resolve
POST /workspaces/{workspace_id}/findings/{finding_id}/reject
GET  /workspaces/{workspace_id}/findings/{finding_id}/history
```

Список поддерживает отбор по состоянию, приоритету и проекту. По умолчанию
возвращаются открытые и переоткрытые карточки: сначала критические, затем
высокие, средние и низкие.

### Правила решений

- подтверждение переводит `open` или `reopened` в `acknowledged`;
- откладывание требует будущую дату и непустую причину;
- закрытие требует комментарий длиной не менее 10 символов;
- отклонение требует код причины из заданного списка и комментарий;
- отклонение переводит карточку в состояние `rejected`;
- закрытую или отклонённую карточку нельзя изменить обычной командой;
- каждое решение содержит автора и время и добавляется в историю;
- состояние меняется только при совпадении переданного номера версии карточки.



### Пошаговая реализация

1. Сначала реализуйте службу и хранилище в памяти.
2. Проверьте допустимые переходы состояний.

6. Реализуйте маршруты как тонкие оболочки над службой.

8. Добавьте отбор и устойчивую сортировку списка.
9. Проверьте приложение через `httpx` в памяти, без сетевого порта.
10. Добавьте ручной запуск через `uvicorn`.



### Как выглядит карточка

Ответ подробного маршрута содержит клиента, проект, приоритет, объяснение,
рекомендацию, уверенность, версию анализатора, все сообщения-основания и всю
историю решений. В списке возвращается сокращённое представление без полного
текста истории.

### Обязательные проверки

- порядок очереди соответствует приоритетам;
- карточка показывает все основания;
- неверный переход возвращает 409;
- дата откладывания в прошлом возвращает 422;
- второй запрос со старым номером версии возвращает 409;
- история не теряет автора и комментарий;
- запрос `south` к карточке `north` возвращает 404, а не раскрывает её наличие.

## Работа 10. Повторный прогон и измерение качества



### Зачем это нужно

Изменение правил, системной инструкции или модели может улучшить один тип
ситуаций и ухудшить другой. Нужен повторяемый прогон размеченных переписок с
отчётом по каждому типу.

### Что создать

Пакет `quality_replay`:

```text
models.py
dataset.py
matcher.py
metrics.py
report.py
cli.py
```

Используйте `evals/dataset.jsonl`, `evals/predictions-v1.jsonl` и
`evals/predictions-v2.jsonl`.

### Сопоставление

Ожидаемая и найденная ситуации совпадают, если равны рабочая область, беседа,
тип и `subject_key`. Совпадение только текста описания запрещено. Отдельно
проверяется, содержит ли найденная ситуация все обязательные основания.

### Метрики

Для каждого типа и для всего набора рассчитайте:

- верно найдено;
- найдено лишнего;
- пропущено;
- точность среди найденного;
- полнота;
- гармоническое среднее точности и полноты;
- доля совпадений с правильными основаниями;
- число полных дубликатов.

При делении на ноль возвращайте `0.0` и явно проверяйте этот случай. Значения в
JSON округляйте до четырёх знаков только при выводе, а не во время расчёта.

### Порог готовности

Файл `policies/quality-gate.json` задаёт минимальную точность, полноту и долю
правильных оснований для каждого типа. Команда `check` завершается ненулевым
кодом, если нарушен хотя бы один порог, и перечисляет все нарушения.

### Пошаговая реализация

1. Проверьте уникальность идентификаторов примеров.
2. Загрузите эталоны и предсказания строгими моделями.
3. Сопоставьте ситуации по составному ключу.
4. Посчитайте три основных счётчика.
5. Рассчитайте метрики без раннего округления.
6. Проверьте основания только у совпавших ситуаций.
7. Найдите дубликаты.
8. Сформируйте отчёт JSON и короткую таблицу Markdown.
9. Реализуйте проверку порогов.
10. Сравните версии 1 и 2 и покажите изменения по типам.
11. Добавьте необязательную команду `run-llm`, которая вызывает VseLLM только при
    явном флаге, сохраняет результаты отдельно и затем оценивает их тем же кодом.



### Ожидаемый итог

Версия 1 намеренно не проходит порог: в ней есть пропуск просрочки, лишняя
претензия и неверное основание запроса документа. Версия 2 должна пройти все
пороги. Отчёт сравнения обязан показать числовую разницу, а не только слова
«лучше» или «хуже».

Настоящий прогон VseLLM не имеет заранее гарантированного результата и не входит
в обычную приёмку. Он нужен, чтобы сравнить правила, зафиксированную заглушку и
выбранную модель. Отчёт такого прогона сохраняет точный идентификатор модели,
версию системной инструкции, время анализа и расход токенов.

### Обязательные проверки

- идеальный результат даёт все показатели `1.0`;
- пустые ожидания и ответы не вызывают деление на ноль;
- лишний дубликат учитывается;
- правильный тип с неверным `subject_key` считается одновременно пропуском и
лишним результатом;
- неверное основание ухудшает только показатель оснований;
- все нарушения порогов выводятся одним запуском;
- версия 2 проходит готовый порог.
- команда обычной проверки никогда не вызывает VseLLM;
- результат ручного LLM-прогона можно оценить без повторного сетевого вызова.

## Работа 11. Сквозное приложение ResponseFlow



### Зачем это нужно

Последняя работа соединяет механизмы в маленький, но законченный цикл: импорт,
анализ, устранение повторов, приоритет, очередь, решение человека и повторная
проверка. Она показывает границы частей будущего ActionFlow без сложной
инфраструктуры.

### Что создать

Пакет `responseflow_local`:

```text
domain/messages.py
domain/findings.py
application/import_messages.py
application/analyze.py
application/review.py
application/report.py
detectors/unanswered.py
detectors/commitments.py
detectors/semantic_llm.py
llm/provider.py
llm/fake_provider.py
llm/vsellm_provider.py
storage/sqlite.py
api/main.py
cli.py
```

Разрешается переиспользовать собственный код из предыдущих работ с указанием
происхождения в README. Простое копирование без объединяющих проверок не
считается завершённой работой.

### Команды

```text
init-db       создать пустую базу
import-data   загрузить сообщения и каталоги
analyze       запустить все три анализатора на фиксированное время
list          показать очередь
show          показать карточку и основания
review        записать решение менеджера
report        показать сводку по состояниям и типам
```



### Сквозной сценарий

1. Создать новую SQLite-базу.
2. Импортировать полный набор сообщений.
3. Запустить анализ на `2026-09-15T15:00:00+03:00` с программной заглушкой LLM.
4. Получить очередь без дубликатов.
5. Открыть карточку просроченной сметы и увидеть сообщение `n-001-006`.
6. Подтвердить карточку от имени `manager-olga`.
7. Закрыть её с содержательным комментарием.
8. Повторить анализ тех же данных: новая карточка не появляется и закрытая не
  переоткрывается.
9. Импортировать `messages/new-evidence.jsonl`.
10. Повторить анализ: карточка получает новое основание и переоткрывается.



### Границы частей программы

В предметном коде нет импортов FastAPI, Typer и SQLite. Анализаторы получают
готовое окно переписки, а не читают файлы сами. Хранилище реализует собственные
интерфейсы репозиториев. Точка сборки приложения явно создаёт зависимости.
Поставщик LLM также выбирается в точке сборки: заглушка используется по
умолчанию, а VseLLM включается только явной настройкой.

### Минимальный отчёт

Команда `report` показывает:

- число карточек по типам и состояниям;
- число карточек по уровням приоритета;
- среднее время от первого обнаружения до решения;
- число повторных обнаружений;
- число переоткрытий;
- долю подтверждённых и отклонённых карточек.

Для отсутствующих данных выводится `0`, а не ошибка или выдуманное значение.

### Обязательные проверки

- полный сценарий выполняется во временной базе;
- повтор импорта и анализа не создаёт дубликатов;
- все карточки имеют существующие основания;
- решение сохраняется после перезапуска приложения;
- закрытая карточка переоткрывается только при новом основании;
- ошибка одного анализатора записывается в отчёт запуска, а результаты остальных
сохраняются;
- `north` и `south` никогда не смешиваются;
- команды возвращают ненулевой код при неверных данных;
- программный интерфейс и командная программа используют одну прикладную службу;
- результат версии анализатора и время запуска сохраняются для аудита.
- обычные проверки не вызывают LLM по сети;
- отдельная ручная команда анализирует одну синтетическую беседу через VseLLM и
  сохраняет имя модели, версию запроса и расход токенов без сохранения ключа.



### Как выглядит готовое решение

Наставник клонирует только каталог работы, выполняет команды из README и получает
одинаковую очередь. Затем он повторяет анализ, закрывает одну карточку, добавляет
готовое новое основание и видит ровно одно переоткрытие. Все действия объяснимы
через историю и точные сообщения. Основной сценарий не использует сеть; вызов
VseLLM выполняется отдельной явной командой.
